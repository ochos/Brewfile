## 選定

### 第1候補: DWDM / 光伝送（#1〜4）

**なぜこれか**

1. **本人が「綺麗にまとまっているサイトが無い」と証言している。** ネタ選びの条件そのもの
2. **10年の実務経験は AI で複製できない。** 2026年に最も価値が上がる種類の参入障壁
3. **読者が明確**: 通信キャリア・DC事業者・ベンダー・SIer に配属された新人と、異動してきた人。「10年前の自分」が読者
4. **Zenn/Qiita に競合記事がほぼ無い** → 検索で即上位に立てる
5. **現職の DC 事業と隣接**している。将来の商品（#14,15）へ地続きでつながる

**弱点**: 市場が小さい。ただし M1 は **500円 × 2冊 = 月1,000円** なので、母数の小ささは問題にならない。むしろ競合ゼロの利点が勝る。

### 第2候補: 古民家 → 宿泊施設（#5,6）

**強み**: **守秘義務のリスクがゼロ**（完全に個人の話）。しかも**これから手続きするので、リアルタイムで記録できる**。旅館業法・用途変更・消防法まわりは情報が断片的で、実際にやった人の記録に価値がある。

**弱み**: プラットフォームが Zenn ではなく **note** になる。技術記事とは集客の経路が別になるため、二正面作戦になる。

→ **M1 では第1候補に集中し、これは M2 以降の第2商品として温存する。**

### #26 の評価（Claude Code そのものをネタにする件）

**有料商品としては弱い。無料記事としてなら価値がある。**

| 論点 | 評価 |
|---|---|
| 「まだ勉強中」である | **本の条件を満たさない。** 本プロジェクトの基準は「自分が詰まって、**実際に解決した**こと」。解決前のものは解説として書けない |
| 陳腐化が速い | AIツールの仕様は数ヶ月で変わる。買い切り本にすると、売った直後に古くなる |
| 競合 | 市場調査で「Claude Code 副業」系の検索結果は**大半がAI生成のランクC記事**と判明済み。飽和領域 |
| 提供元が内製してくる | 公式ドキュメントとチュートリアルが改善されれば、解説記事の価値は消える（AIラッパーと同じ構造） |

**ただし、無料記事としてなら有効。** 「他のチャットAIから来た人が最初に戸惑う点」は検索需要があり、**今まさに戸惑っている本人が書けば一次情報になる**。解説ではなく**つまずきの記録**として書く分には、正直さがそのまま価値になる。

→ ただし DWDM とは読者層が完全に別で、集客が分散する。**M1 では書かない。**

### #27 が本命候補（#26 の正しい使い方）

「Claude Code 入門」は飽和している。しかし **「データセンター／インフラの担当者が、Claude Code で運用管理ツールを自作する」** は誰も書いていない。

- AI ツールの話（読者が多い）× インフラ運用の実務（書ける人が少ない）の**掛け算**
- #14「DC運用管理支援ツール」・#15「キャパシティ管理ツール」と**同じ作業から生まれる**
- 作ったツールそのものが M2/M3 の商品になりうる

**差別化しているのは AI の側ではなく、ドメインの側。** これは #1（DWDM）と同じ構造の勝ち方。

## 守秘義務の取り扱い（最重要）

**#1〜4 と #9〜16 は、書き方を誤ると守秘義務違反になる。** 特に:

- 前職（Colt）の**社内ドキュメント由来の知識**
- 現職の**買収・引き継ぎ中の情報**（M&A 進行中は最も危険）

### 書いてよいもの / いけないもの

| 書いてよい | 書いてはいけない |
|---|---|
| ITU-T などの**公開標準**（G.694.1 のグリッドなど） | 社内ドキュメントの記載内容 |
| **ベンダーの公開ドキュメント**・製品カタログの内容 | 会社固有の設計値・閾値・運用手順 |
| 一般的な技術原理と、その**つながりの説明** | 顧客名・回線名・ネットワーク構成 |
| 「**どこが分かりにくいか**」という自分の体験 | 障害事例の具体的な内容・日時・影響範囲 |
| 自分で再現・検証できる範囲 | 買収・引き継ぎに関する一切の情報 |

### 実務ルール

> **経験は「地図」として使い、内容は公開情報からゼロで再構成する。**

10年の経験の価値は「何が書いてあるか」ではなく「**どこでつまずくか、何と何が繋がっているか**」を知っていること。これは公開情報だけを使っても書ける。そして、それこそが既存のベンダー資料に欠けている部分。

**判断に迷ったら書かない。** 現職の就業規則に秘密保持条項があるはずなので、そちらも確認すること。前職の秘密保持義務は**退職後も継続する**のが通常。

### Ciena 寄りにすることの効果と注意

**効果（大きい）**

- 「Ciena 6500」「WaveLogic」等は**日本語の情報がほぼゼロ**。検索すれば即上位に立てる
- 読者が実際に検索するのは一般語ではなく**製品名**。集客上これは有利
- 市場シェアが大きい ＝ 読者の母数がある

**注意（新たに発生したリスク）**

| | |
|---|---|
| **Ciena の技術資料は大半が顧客ポータルの中にある** | ログインが必要な資料は**参照元にできない**。ライセンス・NDA の対象 |
| 使ってよいもの | 一般公開されているデータシート、ホワイトペーパー、プレスリリース、製品ページ |
| 判断基準 | **「ログインせずに URL を開けるか」**。開けないものは出典にしない |
| 前職との距離 | Ciena 寄りにすると前職の業務と近づく。**製品の一般的な仕様**は書けるが、**そこで何をどう設定していたか**は書けない |

> **実務ルール**: 引用元の URL を必ず記録し、それが**未ログインで開けること**を確認してから書く。開けない資料の内容は、記憶からでも書かない。
