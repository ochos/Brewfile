## 1. 公開方式の選択 — Web エディタ vs GitHub 連携

### 1-1. 比較表

| 観点 | Web エディタ方式 | GitHub 連携方式 |
|---|---|---|
| 初期セットアップ | 不要。ブラウザで即書ける | リポジトリ作成 + CLI 導入で30〜60分 |
| 執筆場所 | zenn.dev 上のエディタ | ローカルの好きなエディタ（VS Code 等） |
| **Claude Code から編集** | **できない**（ブラウザ操作が必要） | **できる**（ただのローカル Markdown ファイル） |
| バージョン管理 | なし（履歴が残らない） | Git の履歴が全部残る。事故っても戻せる |
| 下書きの一括管理 | 記事ごとにバラバラ | `articles/` 配下に全部並ぶ。grep も置換もできる |
| プレビュー | エディタ内でリアルタイム | `npx zenn preview`（localhost:8000）［ソース確認済］ |
| 必要な Git 知識 | ゼロ | `add` / `commit` / `push` の3つだけ |
| 有料本の原稿の秘匿 | Zenn 内に閉じる | **リポジトリを Private にしないと原稿が丸見え**［未確認］ |
| 両方使ったとき | — | GitHub 側が「正」。Web で編集しても次のデプロイで上書きされる［未確認］ |

### 1-2. 結論: **GitHub 連携方式を推奨する**

理由は3つ。優先度順。

1. **Claude Code が使えるかどうかが、この案件では決定的だから。**
   本人の技術レベルは「少し書ける」、稼働は週5〜10時間。この条件で技術記事と技術書を量産する唯一の現実的な手段は Claude Code に草稿を書かせてレビューすることである。Web エディタ方式ではその主力ツールが使えず、ブラウザへのコピペ作業が毎回発生する。**GitHub 連携は「Claude Code を執筆に使えるようにするための必須条件」**であって、Git 好きのための選択肢ではない。

2. **Git が苦手なことは、この方式のデメリットにならない。**
   Zenn の運用で使う Git 操作は `git add . && git commit -m "..." && git push` の3コマンドだけで、ブランチ運用もマージもプルリクも不要である。しかもその3コマンドすら Claude Code に「push して」と言えば代行させられる。**「Git が苦手」という制約は、Claude Code の存在によって実質的に消えている。**

3. **本を売るなら、原稿の一括管理と履歴が効いてくる。**
   Books はチャプター単位のファイルの集合になる。章の並べ替え、価格変更、無料公開範囲の調整を繰り返すことになるが、Web エディタでは「どこをいじったか」の記録が残らない。有料販売する以上、購入者から指摘が入ったときに「いつ何を直したか」を追えることには実利がある。

### 1-3. ただし、この条件下では以下に注意

- **有料本を書くリポジトリは Private にする。**［未確認］Public にすると、有料チャプターの原稿が GitHub 上で誰でも読めてしまう。Zenn の GitHub App は Private リポジトリでも連携できる。
- **Web エディタは「緊急の誤字修正」用と割り切る。**［未確認］GitHub 連携中は GitHub 側が正なので、Web で直しても次の push で消える。直したらローカルにも同じ修正を入れること。

## 2. GitHub 連携のセットアップ（要点）

**具体的な実行手順は [`../publish/SETUP.md`](../publish/SETUP.md) に、コピペできる形で分離した。** ここには判断に必要な事実だけを書く。

### 2-1. 必要な Node.js のバージョン

**Node.js 22.12.0 以上**［npm確認済］

- `zenn-cli` の最新版は **0.5.3**（2026-08-26 公開）で、その `package.json` の `engines` は `{"node": ">=22.12.0"}`。
- 0.5.3-alpha.3 までは `>=22.0.0` だったが、alpha.4（2026-08-25）で `>=22.12.0` に引き上げられている。つまり**要求バージョンは最近上がったばかり**なので、古い記事の「Node 14 以上」という記述は現在は誤り。
- 実務上は **Node.js 22 LTS の最新版か、24 系**を入れておけばよい。
- 確認コマンド: `node -v`

### 2-2. zenn-cli の入れ方と主要コマンド［ソース確認済］

グローバルインストールは不要で、プロジェクトのローカル依存として入れる。

| コマンド | 動作 |
|---|---|
| `npx zenn init` | `articles/` `books/` `.gitignore`（`node_modules` と `.DS_Store` を記載）`README.md` を生成。既存ファイルはスキップする |
| `npx zenn new:article` | `articles/{slug}.md` を生成 |
| `npx zenn new:book` | `books/{slug}/` に `config.yaml` と `example1.md` `example2.md` を生成 |
| `npx zenn preview` | ローカルプレビューサーバを起動。**デフォルトポートは 8000** |
| `npx zenn list:articles` / `list:books` | 一覧表示 |
| `npx zenn --version` / `zenn help` | バージョン / ヘルプ |

**`new:article` のオプション**［ソース確認済］

| オプション | 型 | 既定値 |
|---|---|---|
| `--slug` | 文字列 | 自動生成 |
| `--title` | 文字列 | 空文字 |
| `--type` | 文字列 | `tech`（`idea` 以外を指定すると `tech` に丸められる） |
| `--emoji` | 文字列 | 48種類からランダム |
| `--published` | 文字列 | `false`（文字列 `"true"` のときだけ true 扱い） |
| `--publication-name` | 文字列 | 空（指定時のみ frontmatter に出力） |

**`new:book` のオプション**［ソース確認済］: `--slug` / `--title` / `--published`（既定 false）/ `--summary` / `--price`（数値、既定 0）

**`preview` のオプション**［ソース確認済］: `--port`（`-p`、既定 **8000**）/ `--host` / `--open`（ブラウザ自動起動）/ `--no-watch`（ファイル監視を切る）。既定では `articles` と `books` ディレクトリを監視して自動リロードする。

### 2-3. 連携の流れ［未確認・検索スニペット由来］

1. GitHub で空のリポジトリを作る（Private 推奨）
2. Zenn にログイン → ダッシュボード → **「GitHubからのデプロイ」** → **「リポジトリを連携する」**
3. GitHub の App インストール画面に遷移 → **「Only select repositories」** を選び、作ったリポジトリだけを選択 → **「Install」**
4. 同期対象ブランチは既定で `main`。ダッシュボードのリポジトリ設定タブから変更できる
5. 以降、対象ブランチに push すると自動でデプロイされる

**注意点**［未確認］
- **連携できるリポジトリは最大2つ。** 3つ以上選ぶと連携に失敗するという報告がある。
- **push が成功しても Zenn 側のデプロイが成功したとは限らない。** 必ずダッシュボードのデプロイ履歴（`/dashboard/deploys`）で結果を確認すること。
- **非公開のレート制限がある。** 「直近24時間で5本以上投稿するとブロックされる」という複数の報告がある。しかも**制限時間が明けても自動では再判定されず、新しいコミットを push し直す必要がある**とのこと。→ 記事の一括投入をやってはいけない。1日1〜2本までに抑える。

### 3-1. 構成［ソース確認済］

└── books/

        ├── config.yaml        ← 本の設定

### 3-2. 記事の frontmatter — 全項目と制約

Zenn 公式のバリデータ実装（`zenn-model/src/utils.ts`）を直接読んで確認した。**［ソース確認済］**

```yaml
---
title: "Claude Code で光ファイバのOSNR計算を自動化した"   # 必須・70字以内
emoji: "🔦"                                              # 必須・絵文字ちょうど1つ
type: "tech"                                             # 必須・"tech" か "idea" のみ
topics: ["claudecode", "python", "光ファイバ"]            # 必須・1〜5個
published: true                                          # 必須・true / false（真偽値）
published_at: 2026-09-01 09:00                           # 任意・予約投稿用
publication_name: "myteam"                               # 任意・Publication に出すとき
---
```

| 項目 | 必須 | 制約［ソース確認済］ | 実装上のエラーメッセージ |
|---|---|---|---|
| `title` | 必須 | 文字列、**70字以内** | 「タイトルは70字以内にしてください」 |
| `emoji` | 必須 | **絵文字ちょうど1つ**。アイキャッチとして使われる | 「絵文字（emoji）を1つだけ指定してください」 |
| `type` | 必須 | **`tech` または `idea` のみ**。`tech` = 技術記事、`idea` = アイデア・ポエム | 「type に tech または idea を指定してください」 |
| `topics` | 必須 | 文字列の配列。**1個以上5個以下**、各**18字以内**、**記号とスペース不可**（C++ は `cpp`、C# は `csharp`） | 「topicsは最大5つまで指定できます」他 |
| `published` | 必須 | **真偽値**（`true` / `false`）。クオートで囲むと型エラー | 「published を true/false で指定してください」 |
| `published_at` | 任意 | `YYYY-MM-DD` または `YYYY-MM-DD hh:mm`（正規表現 `^[0-9]{4}-[0-9]{2}-[0-9]{2}(\s[0-9]{2}:[0-9]{2})?$`）。**未来日時を指定する場合は `published: true` が必須**。時刻省略時は 00:00 | 「published_at に未来の日時を指定する場合は、published に true を指定してください」 |
| `publication_name` | 任意 | `^[0-9a-z_]{2,15}$`（英小文字・数字・アンダースコアの2〜15字） | 「Publication名は a-z0-9_ の2〜15字」 |

**記事の slug（＝ファイル名から `.md` を除いた部分）**［ソース確認済］
- 正規表現 `^[0-9a-z\-_]{12,50}$`
- **英小文字・数字・ハイフン・アンダースコアのみ、12文字以上50文字以下**
- → `test.md` や `article1.md` は**弾かれる**（12文字未満）。`osnr-calc-with-claude-code.md` のように十分長くすること。
- **slug は記事の URL（`https://zenn.dev/{ユーザー名}/articles/{slug}`）になる。公開後に変えると URL が変わる**ので、最初に決めきること。

**canonical について**: Zenn の記事 frontmatter に **canonical URL を指定する項目は存在しない**。`zenn-model/src/types.ts` の `Article` 型は `slug / title / bodyHtml / toc / emoji / type / topics / tags / published / published_at / publication_name` のみで、canonical 相当のフィールドがない。**［ソース確認済］**（第6章参照）

### 3-4. price に指定できる値 — **500円は指定可能**［ソース確認済］

Zenn 公式実装のバリデータ3本が、そのまま制約の定義になっている。

| バリデータ | 条件 | エラーメッセージ |
|---|---|---|
| `validateBookPriceType` | `typeof price === 'number'` | 「price（本の価格）を半角数字で指定してください（クオテーション " で囲まないでください）」 |
| `validateBookPriceRange` | `price === 0` **または** `200 <= price <= 5000` | 「price（本の価格）を有料にする場合、200〜5000の間で指定してください」 |
| `validateBookPriceFraction` | `price % 100 === 0` | 「price（本の価格）は100円単位で指定してください」 |

したがって:

- **下限: 200円**（有料の場合）
- **上限: 5,000円**
- **刻み: 100円単位**
- **`0` は「無料」として特別に許可される**
- 指定できる値の全リスト: `0, 200, 300, 400, 500, 600, ... , 5000`

> ### **結論: `price: 500` は有効。本プロジェクトの「500円の技術書」はそのまま実現できる。**
> 注意点は2つだけ。**クオートで囲まない**（`price: "500"` は型エラー）、**カンマを入れない**（`1,000` は不可、`1000` と書く）。

### 3-5. チャプターファイルの命名規則と並び順［ソース確認済］

**チャプターの slug**
- `validateChapterSlug` により **英小文字・数字・ハイフン・アンダースコアの1〜50文字**
- 記事 slug と違い、**12文字未満でもよい**（`intro` でOK）
- 加えて **`数字.slug.md`（例: `1.intro.md`）という数字プレフィックス形式**も許容される

**並び順の決定ロジック（`zenn-cli/src/server/lib/books.ts`）**

1. **`config.yaml` の `chapters` に配列で書かれていれば、その順番が正**（これが推奨）
2. `chapters` を書いていない場合は、**ファイル名の `数字.slug.md` の数字を順序として使う**
3. どちらにも当てはまらないチャプターは `position` が `null` になり、**ソート時に 999 番目として扱われて末尾に回る**

**推奨する運用**: **`config.yaml` の `chapters` で明示的に順番を書く。** 理由は3つ。
- 章の入れ替えがファイル名変更なしでできる（ファイル名を変えると URL が変わってしまう）
- どのチャプターが本に含まれるかが1箇所で見える
- `chapters` に書かなければ同期されないので、**書きかけの章をリポジトリに置いたまま公開できる**［未確認］

**チャプターの URL**: `https://zenn.dev/{ユーザー名}/books/{本のslug}/viewer/{チャプターのslug}`。**チャプター slug も公開後は変えないこと。**

### 3-6. 無料公開チャプター（試し読み）の設定方法 ← **重要**

**設定場所は `config.yaml` ではなく、各チャプターの Markdown ファイルの frontmatter。**

```markdown
---
title: "はじめに — この本で何ができるようになるか"
free: true
---

本文...
```

**［ソース確認済］の根拠**
- `zenn-model/src/types.ts` の `Chapter` 型: `{ slug, filename, title?, free?: boolean, bodyHtml?, position }`
- `validateChapterFreeType`: 「free には true か false のみ指定」（`undefined` または真偽値のみ許可）

**仕様と注意点**
- `free: true` を書いたチャプターは、**本を購入していない人でも全文読める**。
- `free` を省略した（＝書かない）チャプターは**有料**扱いになる。
- **本の `price` が 0（無料本）のときは `free` の指定は無視される**［未確認］。全部無料なので当然。
- クオートで囲まないこと。`free: "true"` は型エラーになる。

**500円の本で、購入率を最大化する試し読み設計（推奨）**

| チャプター | free | 役割 |
|---|---|---|
| 1. はじめに（誰向けか・何ができるようになるか・前提知識） | **true** | 「自分向けの本か」を判定させる。ここでミスマッチを弾くと返金・低評価が減る |
| 2. 最初の実践章（1つ完結する具体例を最後までやりきる） | **true** | **ここが購入判断の核心**。「この粒度と文体で残りも書かれている」と示す。目次だけ見せても買われない |
| 3章以降 | 指定なし（有料） | 本体 |
| 最終章「まとめ・付録」 | 指定なし（有料） | |

設計の要点は、**「無料章を読み終えた時点で、読者が1つ成果を得ていて、かつ次の疑問が生まれている」状態を作ること。** 導入だけを無料にして「続きは有料」で切ると、読者は価値を測れないまま離脱する。逆に無料章で完結してしまうと買う理由が消える。**「1つ解決 → 応用でつまずくポイントを提示 → その解決は3章」**という構成が、500円の技術書では最も効く。

### 3-7. 表紙画像（cover）［ソース確認済］

| 項目 | 仕様 |
|---|---|
| 置き場所 | `books/{本のslug}/` 直下 |
| ファイル名 | `cover.png` / `cover.jpg` など（`cover` + 対応拡張子） |
| ファイルサイズ | **1MB 以内**（「カバー画像は1MB以内にしてください」） |
| 縦横比 | **幅:高さ = 1:1.4 を推奨**。最終的に **500px × 700px** にリサイズされる |
| 未配置時 | 「本のカバー画像を /books/{slug} ディレクトリに配置してください」という検証エラーが出る |

→ **500 × 700 px の PNG を作るのが最も安全。**

## 4. 販売まわり

> **この章の数値は全て［未確認］である。** zenn.dev への直接アクセスが遮断されており、検索スニペット経由でしか確認できていない。**販売開始前に必ず https://zenn.dev/faq/sales を自分のブラウザで開いて再確認すること。**

### 4-1. 販売手数料［未確認 / 確認時点 2026-08-30］

**2段階で引かれる。**

1. **決済手数料 = 販売価格の 3.6%**
2. **Zenn プラットフォーム利用料 = （販売価格 − 決済手数料）の 10%**

つまり著者の受取率は `(1 − 0.036) × (1 − 0.10) = 0.8676` = **約86.76%**、**実効手数料は約13.24%**。

**公式の計算例**（1,000円の本の場合）: `(1000 − 1000 × 0.036) × 0.9 = 868円`

**本プロジェクト（500円）に当てはめると**

| 項目 | 金額 |
|---|---|
| 販売価格 | 500円 |
| 決済手数料 3.6% | −18円 |
| 小計 | 482円 |
| Zenn 利用料 10% | −48.2円 |
| **1冊あたりの受取額** | **約433円**（端数処理の方法は未確認） |

> **重要な帰結: 「月商1,000円 = 500円 × 2冊」でも、実際の手取りは約867円である。**
> さらに振込時に 350円が引かれる（次項）。M1 の達成判定を「売上1,000円」で見るのか「入金1,000円」で見るのかを、あらかじめ決めておくこと。`12-economics.md` の記載（500円商品の手取り 約350〜400円）は、この計算だと **約433円**が正しい見込み。

出典: https://zenn.dev/faq/sales （※未読）、検索スニペットおよび複数の実践記事

### 4-2. 売上の確認方法・振込［未確認］

| 項目 | 内容 |
|---|---|
| 売上の確認 | **Zenn ダッシュボード内**で確認する。振込先口座もダッシュボードで設定する |
| **振込手数料** | **1回あたり 350円**（申請のたびに引かれる） |
| **現金で受け取る最低額** | **未払い残高 1,000円以上**。1,000円未満の場合は **Amazon ギフト券**での受け取りを選べる |
| 振込のタイミング | 自動振込ではなく **申請ベース**（申請 → 数営業日で入金）。締め日・入金日の詳細は**未確認** |
| **放置した場合** | 確定日から **5ヶ月以内**に振込申請しないと、**同額の Amazon ギフト券を申請したものとして処理される**（失効はしない） |

**運用上の結論**: **毎月出金してはいけない。** 500円の本が月2冊（受取 約867円）のペースだと、毎月出金すれば 350円 = 手取りの約40%が振込手数料に消える。**残高が数千円たまるまで貯めてから、まとめて1回申請する**のが合理的（`research/02-monetization-legal.md` の記載とも一致）。ただし **5ヶ月ルール**があるので、放置しすぎると Amazon ギフト券に切り替わる点だけ注意。

### 4-3. 販売に必要な本人確認・口座登録［未確認・情報不足］

**検索では、Zenn が本人確認書類（免許証・マイナンバー等）の提出を求めるという記述を確認できなかった。** 確認できたのは以下だけ。

- 振込先（銀行口座）は **Zenn ダッシュボード内で登録する**
- `research/02-monetization-legal.md` の整理でも、Zenn は「審査なし / 必要なもの: 銀行口座」と記載されている

**したがって現時点の想定は「銀行口座の登録のみで、本人確認書類の提出は不要」だが、これは未確認である。** 実際には支払調書や税務対応のためにマイナンバーの提出を求められる可能性がある（他プラットフォームでは一般的）。**販売設定を開いた時点で実際の入力項目を確認し、この文書を更新すること。**

**顔出しNG・実名OKという本人の条件との関係**
- Zenn Books は**プラットフォーム側（運営会社）が販売主体**となる形式であり、**著者個人の住所・電話番号を商品ページに表示する必要はない**という理解［未確認］。特定商取引法に基づく表記は Zenn 側のページ（https://zenn.dev/terms/transaction-law）に集約されている。
- **これは Zenn を選ぶ大きな理由の一つ**である。自前決済（Stripe 直販）や一部プラットフォームでは、個人でも住所・氏名・電話番号の表示義務が生じる。
- **ただし必ず販売前に https://zenn.dev/terms/transaction-law を開いて、著者個人の情報開示が必要かどうかを自分の目で確認すること。**

### 4-4. 審査の有無・公開までの時間［未確認］

- **事前審査はない。** 有料本であっても、`published: true` にして push すれば、Zenn 側のデプロイ処理が完了した時点で公開・販売開始になる。
- 公開までの時間は **push からおおむね数十秒〜数分**。ただし**「push が成功 = 公開成功」ではない**ので、ダッシュボードのデプロイ履歴で必ず確認すること。
- 第2章の**非公開レート制限**（直近24時間で5本以上でブロック）に該当すると、push しても静かに公開されない。**エラー通知が来ないのが厄介**。

## 6. Zenn の規約上の注意

> この章も基本的に［未確認］。**https://zenn.dev/terms と https://zenn.dev/guideline を必ず自分で読むこと。**

### 6-1. 自己宣伝・アフィリエイト［未確認 / 確認時点 2026-08-30］

**2025年6月5日に利用規約とコミュニティガイドラインが改定されている。** 改定の主眼は以下の3点とされる。

1. **広告や採用を主な目的とする記事を、違反対象として明示した**
2. コミュニティガイドラインを、利用規約上の禁止行為の解釈を補うものと位置づけた
3. 生成AI 利用に関するガイドラインを示した

**自己宣伝について**
- **記事の主目的が製品・サービス・採用の宣伝である投稿は違反となりうる。**
- 許容範囲は「**記事末尾の固定メッセージ程度**」というのが実務上の理解［未確認］。

**アフィリエイトについて**
- **一律禁止とはされていない**とみられる［未確認］。技術記事の参考文献として書籍リンク等を貼るのは許容される一方、**明らかにアフィリエイト収益が主目的の記事はアウト**という解釈。

**生成AI について（本プロジェクトに直結）**
- **AI 執筆は禁止されていない。** ただし「内容の正確性を確認せずに投稿すること」「フォロワー獲得やスコア上昇を目的に記事を乱造すること」は控えるよう明記されている。
- **クリックベイト（誇張タイトル）と著作権侵害も禁止。**

> **本プロジェクトへの含意**: Claude Code に記事を書かせる運用そのものは規約上問題ない。**問題になるのは「検証せずに出す」「量で押す」の2つ。** 前述のレート制限（24時間で5本）も、この方針と整合している。**記事は1日1本まで、必ず自分で検証してから出す**というルールを最初から敷くこと。
>
> **有料本への導線について**: 記事の末尾に「詳しくは本にまとめました」と1ブロック置くのは許容範囲とみられるが、**「本を売るための記事」に見える構成（本文が薄く、宣伝が主）は違反リスクがある。** 記事は単体で完結した価値を持たせ、本への導線は末尾の固定フォーマットに限定するのが安全。

### 6-2. 転載・クロス投稿（Qiita への同時投稿）

**Qiita に同じ記事を出してよいか**: **自分が書いた記事であれば、規約上の禁止は確認されていない**［未確認］。実際に Zenn と Qiita に同じ記事を投稿し、GitHub リポジトリで一元管理している事例は複数ある。

**ただし canonical の指定はできない。**

- **Zenn の記事 frontmatter に canonical URL の項目は存在しない**［ソース確認済］（`Article` 型にフィールドがない）
- Qiita 側にも canonical 指定機能はないとされる［未確認］

**結果として起きること**（SEO 上のリスク）
- 同一内容が複数 URL に存在すると、Google がどちらを正規版とするかを自分で判断する
- 被リンク・クリック率などの評価シグナルが2つの URL に分散する
- 最悪の場合、両方が重複コンテンツと判定されうる

**推奨する運用（この案件での結論）**

1. **Zenn を「原本」と決める。** 本の販売基盤が Zenn にある以上、評価を Zenn 側に集約するのが合理的。
2. **必ず Zenn に先に公開し、数日おいてから Qiita に出す。** 公開順が Google のクロール履歴に残る。
3. **後から出した側（Qiita）の冒頭に「この記事は Zenn に投稿したものの転載です」+ 原本へのリンクを必ず書く。** canonical が使えない以上、正規版を伝える手段は本文しかない。
4. **可能なら、まるごとコピーせず構成を変える。** タイトル・導入・見出し構成を変え、内容の半分程度を再構成すると重複判定を避けやすい。
5. **月商1,000円の段階では、そもそもクロス投稿を後回しにしてよい。** 週5〜10時間の稼働で2媒体を運用すると、1本あたりの品質が落ちる。**まず Zenn 単独で回す**ことを推奨する。

## 9. この文書の要点（3行）

1. **`price: 500` は指定可能。** Zenn 公式実装のバリデータで「0 または 200〜5000、100円単位」と確認済み。**この案件の前提は技術的に成立する。**
2. **手数料は 決済 3.6% → 残額に 10% の2段階で、実効 約13.24%。500円の本1冊の手取りは約433円。** 加えて振込1回 350円・最低残高 1,000円なので、**出金は数ヶ月ためてから1回**が正解。
3. **試し読みは `config.yaml` ではなく、チャプター側の frontmatter に `free: true`。** 導入章と「最初の実践章」の2つを無料にし、無料章で1つ成果を出させてから次の壁を見せる構成が、購入率に最も効く。
